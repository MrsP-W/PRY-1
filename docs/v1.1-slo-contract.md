# v1.1 SLO 设计契约（D6.13.3）

> **状态：design-only。** 本文只冻结指标、阈值和告警数据契约。P3 观察期内
> 不接入运行时、不发送通知、不修改 LaunchAgent、SMTP、Feature Flag、
> `ENABLE_*`，也不读写真实 Notes、SAP 或财务数据。

## 1. 结论

v1.1 使用恰好 5 个 SLO 维度：可用性、新鲜度、结果质量、响应时延和安全合规。
所有指标遵守三态判定：`pass`、`breach`、`unknown`。输入缺失、损坏或窗口不完整
一律是 `unknown`，不得按 `pass` 计算。

SLO 是运行目标，不是发布授权。P3 的 7 天无人干预和 30 天无 P0/P1 仍是独立硬门；
任一完整日报出现 `attention`，即使某个 SLO 达标，也不能据此取得或恢复 P3 资格。

## 2. 适用范围与非目标

### 2.1 适用范围

- 对本地 health、news、离线评测和未来脱敏审计信号提供统一计算口径。
- 对每个 SLO 固定 SLI、窗口、目标、告警和恢复条件。
- 为 P3 后的只读报告或看板提供版本化输入契约。

### 2.2 非目标

- 不实现采集器、告警器、看板、数据库、调度或通知渠道。
- 不改变现有 `p3_burn_in_report.py` 的资格规则和 attention 规则。
- 不把 Feature Flag 当作权限，也不自动开启、关闭或回滚任何能力。
- 不定义真实邮件、Notes、SAP、财务或第三方账户的写入流程。
- 不用当前阈值反推或覆盖历史 P3 证据。

## 3. 通用计算规则

| 项 | 契约 |
| --- | --- |
| 时间 | UTC；正式日结只使用完整 UTC 日，滚动窗口仅用于预警。 |
| 窗口 | 默认滚动 24 小时预警、完整 UTC 日定稿、连续 7 个完整日看趋势。 |
| 生命周期 | `inactive` 不计算、不告警也不显示 PASS；经审批成为 `active` 后才进入三态判定。本文 5 项当前均为 `inactive`。 |
| 分母为 0 | 判为 `unknown`，禁止用空集合得到 100%。 |
| 输入完整性 | 任一必需 journal 不可用、坏行大于 0、时钟倒退或 schema 不兼容，相关 SLO 判为 `unknown`。 |
| 聚合 | 先按 `scope` 分组，再计算整体；任一关键 scope 为 `breach` 或 `unknown` 时，整体不得为 `pass`。 |
| 舍入 | 先用原始整数比较阈值，百分比只用于展示，保留两位小数。 |
| 证据保留 | `resolved` 只关闭当前告警，不删除 breach；历史 attention 仍参与 P3 资格。 |

`scope` 是稳定、脱敏的能力或来源 ID，例如 `health_monitor`、`news_refresh`、
`email_draft`；禁止使用邮箱、主题、正文、SAP 凭证号或财务明细作为 scope。

## 4. 数据源分级

| 级别 | 含义 | 当前示例 |
| --- | --- | --- |
| `existing` | 当前已有结构化、本地、脱敏数据，可计算 SLI。 | health samples/alerts、news runs、P3 daily/weekly report |
| `partial` | 有样本或测试契约，但缺少统一 runner 或窗口聚合。 | `tests/eval/` fixture 与 schema 测试 |
| `future` | 仅定义字段，不得在 P3 内新增采集。 | capability latency、审批与安全审计摘要 |

路径只作为逻辑来源名进入实现；告警事件不得携带绝对私有路径或原始记录内容。

## 5. 五个 SLO 维度

### SLO-1 可用性（availability）

| 字段 | 定义 |
| --- | --- |
| SLI | `healthy_rate = healthy_samples / total_valid_samples`；同时要求 `opened_alerts = 0`。 |
| 数据源 | `existing`：health samples、health alerts、P3 report 的 `health` 摘要。 |
| 窗口 | 滚动 24 小时预警；完整 UTC 日定稿；7 日趋势。 |
| 目标 | `healthy_rate >= 99.0%` 且 `opened_alerts = 0`。 |
| breach | 任一有效不健康 sample，立即产生 P1 预警；完整日低于目标或出现 opened alert，日结为 `breach`。 |
| unknown | sample journal 不可用、坏行大于 0，或窗口内有效 sample 为 0。 |
| 恢复 | 连续 3 个有效 sample 为 healthy 且当前 alert 已 resolved；仅关闭告警，不抹除日结 breach。 |

说明：现有 P3 attention 对任一不健康 sample 采取更严格的 fail-closed 判定；SLO 的
99% 目标不能放宽该硬门。

### SLO-2 新鲜度（freshness）

| 字段 | 定义 |
| --- | --- |
| SLI | `fresh_rate = intervals_within_limit / total_observed_intervals`，分别按 health 与 news scope 计算。 |
| 数据源 | `existing`：health sample `at`、news run `at`、P3 report 的 gap 摘要。 |
| 窗口 | 滚动 24 小时预警；完整 UTC 日定稿。 |
| 目标 | health 间隔 `<= 30min`、news 间隔 `<= 120min`，且两个 scope 的 `fresh_rate = 100%`。 |
| breach | 任一间隔越界即 P1；沿用现有 `health_sample_gap` 与 `news_run_gap` reason code。 |
| unknown | 任一对应 journal 不可用、坏行大于 0、无有效时间点，或窗口不完整却被用于日结。 |
| 恢复 | 对应 scope 连续 2 个到达间隔不越界且输入完整；历史 gap 仍保留。 |

30/120 分钟是现有报告器的告警边界；15/60 分钟的调度期望可用于看板展示，但不能
在未版本化变更契约前替换判定阈值。

### SLO-3 结果质量（quality）

| 字段 | 定义 |
| --- | --- |
| SLI | `suite_pass_rate = passed_cases / valid_cases`，先按 suite 计算，再取各 suite 的最低值；另计 `schema_valid_rate`。 |
| 数据源 | `partial`：脱敏 `tests/eval/` fixture 与 schema 测试；统一离线 runner 尚未实现。 |
| 窗口 | 每个冻结 fixture 版本的一次完整运行；候选发布前重跑。 |
| 目标 | `schema_valid_rate = 100%`、安全边界 case `= 100%`、每个 suite 的 `suite_pass_rate >= 95%`。 |
| breach | schema 或安全边界 case 任一失败为 P1；普通 suite 低于 95% 或相对已批准 baseline 下降超过 2 个百分点为 P2。 |
| unknown | runner 缺失、fixture 版本未冻结、有效 case 为 0、只跑部分 suite 或结果 schema 无效。 |
| 恢复 | 在同一冻结 fixture 版本上完整重跑并全部达到目标；不得删除失败 case 后宣称恢复。 |

P3 期间只能扩充和校验脱敏 fixture。实现 runner、落库或把评测结果接入运行时属于后续任务。

### SLO-4 响应时延（latency）

| 字段 | 定义 |
| --- | --- |
| SLI | `latency_ms = finished_at - started_at`；按 capability 计算 p50、p95、p99，失败和取消单独计数。 |
| 数据源 | `future`：仅允许未来的脱敏 capability timing 摘要；当前不得新增采集。 |
| 窗口 | 每 capability 最近 24 小时，且至少 20 个有效样本；不足则 `unknown`。 |
| 目标 | 用户等待型本地 AI 操作 `p95 <= 5000ms` 且 `p99 <= 10000ms`。 |
| breach | 两个连续完整窗口 p95 超标为 P2；单次 `>= 30000ms` 或超出调用 deadline 为 P1。 |
| unknown | 样本少于 20、时间戳无效、时钟倒退、缺 scope 或把失败样本静默排除。 |
| 恢复 | 连续 2 个完整窗口达到目标且数据完整；超时事件保留在历史报告。 |

时延只衡量速度，不代表结果正确或允许外部写入；质量和安全维度必须独立通过。

### SLO-5 安全合规（safety）

| 字段 | 定义 |
| --- | --- |
| SLI | `guarded_rate = policy_allowed_attempts / privileged_attempts`，并单列 unauthorized write、敏感内容外泄、审计缺失计数。 |
| 数据源 | `future`：脱敏审批/策略审计摘要；现有测试只能证明契约，不能证明生产期 SLO。 |
| 窗口 | 连续监测；完整 UTC 日定稿；发布候选覆盖整个观察期。 |
| 目标 | `guarded_rate = 100%`；未授权外部写入、敏感内容外泄、审计缺失均为 0。 |
| breach | 未授权写入或敏感内容外泄证据为 P0；审批/策略门被绕过或审计记录缺失为 P1。 |
| unknown | 审计源不可用、schema 无效、分母为 0 或无法证明 privileged attempt 已完整计数。 |
| 恢复 | P0/P1 不自动恢复；需人工结案、保留证据，并按治理流程决定是否开启新观察 epoch。 |

Feature Flag 的 `on` 只允许进入既有安全门，不能把 `guarded_rate` 或人工审批视为已满足。

## 6. 统一告警事件契约

未来实现只能写入脱敏、本地、追加式事件。最小 schema 如下：

```yaml
schema_version: 1
contract_version: "v1.1-slo-draft-1"
event_id: "<uuid>"
event: "opened | updated | resolved"
severity: "P0 | P1 | P2"
slo_id: "availability | freshness | quality | latency | safety"
scope: "<safe-code>"
status: "breach | unknown | recovered"
observed_at: "<RFC3339 UTC>"
window_start: "<RFC3339 UTC>"
window_end: "<RFC3339 UTC>"
actual:
  value: 0
  unit: "percent | count | milliseconds | seconds"
target:
  comparator: ">= | <= | ="
  value: 0
reason_codes: ["<safe-code>"]
consecutive_breaches: 1
dedupe_key: "<slo_id:scope:reason_code>"
source_status: "complete | unavailable | invalid | incomplete"
```

禁止字段：原始邮件地址/主题/正文、Notes 内容、SAP 业务标识、财务明细、凭据、Cookie、
Token、错误正文和绝对私有路径。实现只能记录白名单 reason code 与聚合数字。

## 7. 告警状态机与严重级别

### 7.1 状态机

`pass → opened(breach|unknown) → updated → resolved(recovered)`。

- 同一 `dedupe_key` 只能有一个打开事件；重复观测写 `updated`，不新建告警风暴。
- P1/P2 相同状态的更新冷却 60 分钟；严重级别升级、reason code 变化或恢复立即记录。
- P0 不设冷却，每次新证据均追加；不得自动关闭。
- `resolved` 后再次 breach 使用新 `event_id`，但沿用稳定 `dedupe_key` 便于关联。
- 本契约不指定 SMTP、系统通知或第三方通知；P3 内只允许本地报告展示。

### 7.2 严重级别

| 级别 | 适用条件 | 默认动作（仅契约） |
| --- | --- | --- |
| P0 | 未授权外部写入、敏感数据外泄、不可恢复的数据破坏证据 | fail-closed，需人工审批与事件处理，不自动恢复 |
| P1 | 可用性/新鲜度硬 breach、安全门或审计异常、必需输入 `unknown`、质量安全 case 失败 | 阻断相关资格或候选发布，保留证据 |
| P2 | 有效数据下的普通质量或时延目标未达标 | 记录并进入后续 docs/tests 修复任务 |

## 8. 与 P3 资格和 Feature Flag 的关系

判定优先级从高到低为：安全红线、P3 硬资格门、SLO、Feature Flag 状态。

1. 安全 P0/P1 或输入不可证明完整时 fail-closed。
2. P3 资格继续使用既有 `elapsed_days >= target and not has_attention`；SLO 不改写该公式。
3. SLO `pass` 只说明目标达成，不能启用能力。
4. Feature Flag 还需独立审批；未知、损坏或过期配置仍为 `off`。

因此，缺数据不能制造 PASS，短期恢复不能抵消历史 attention，Flag `on` 也不能绕过审批。

## 9. 版本、变更与后续实现门

- 当前契约版本为 `v1.1-slo-draft-1`；阈值、公式、reason code 或 schema 变化必须升版。
- 变更必须包含 docs 更新、合成测试、旧版兼容/迁移说明和安全回滚方案。
- 当前数据源与未来候选必须分栏展示；不得把 `partial`/`future` 指标标成已监测。
- 指标必须先经版本化任务从 `inactive` 切为 `active`；未激活指标不产生告警，激活后缺数据才判 `unknown`。
- 只有 P3 30 天资格通过且获得用户授权后，才可另开任务实现只读聚合或看板。
- 后续实现仍禁止默认外部通知；任何网络侧效果需独立审批。
